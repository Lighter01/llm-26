## Конфигурация, запуск и Study

| Понятие | Что означает в проекте |
| --- | --- |
| Конфигурация, или пресет | Полный YAML с параметрами корпуса, чанкинга, эмбеддингов, индекса, поиска и оценки. Например, `g2_chunks/overlap_128.yaml`. |
| Запуск (`run`) | Одно выполнение пресета с именем из `--experiment-name`. Его параметры, выдача, метрики и времена сохраняются в `results/<имя>/`. Один пресет можно выполнить несколько раз под разными именами. |
| Группа | Сравнения, отвечающие на один исследовательский вопрос: например, как влияет размер чанка. В обязательной программе это G1–G5. |
| Study | Вся серия связанных экспериментов: группы, их пресеты, контрольные запуски, изменяемые параметры и обоснования выбранных баз. |

**Study** здесь означает «исследование» или «серия экспериментов». Это собственный формат данного проекта. Программа G1–G5 описана ниже и в [анализе экспериментов](../../docs/rag/EXPERIMENTS.md). Файл `study.yaml` оформляет эту программу как проверяемую карту; модели `Study`, `StudyGroup` и `Comparison` и проверки связей находятся в [evaluation/study.py](../../src/dnd_rag/evaluation/study.py).

Карту заполняет автор экспериментов. Она помогает явно зафиксировать, с чем сравнивается вариант и почему выбрана его база. Команды читают карту для проверки связей и построения сводки. Выбор победителей, изменение полных пресетов и переход к следующей группе выполняются автором последовательно; автоматического поиска лучшего набора параметров здесь нет.

## Параметры пресета

YAML выбирается через `--config`; каждый вариант самостоятельный, без наследования. Неизвестные поля, повторные ключи, неверные типы и границы — ошибка. Пути раскрываются от корня lab2, `~` — от home. Имя запуска задаётся только CLI. Локальные адреса — в [.env.example](../../.env.example), LLM — в [отдельном профиле](../llm/local.yaml).

| Поле | Тип / default | Значения и влияние |
| --- | --- | --- |

| chunking.chunk_size | int, 512 | 100..1000 сырых токенов embedding tokenizer. |

| chunking.max_heading_level | int, 4 | 1..6; первичные границы только custom-стратегии. |

| embedding.revision | str, обязательно | Конкретный 40-символьный Git SHA модели и tokenizer. |

## Построение и повторное использование индекса

Для текста используются штатная нормализация модели и косинусное сходство. Плотные векторы хранятся в формате float32 под именем `dense`. У коллекции один шард. Вектор вопроса вычисляется на CPU в формате FP32. При квантовании поиск использует `rescore=false` и `ignore=false`. Длина входа эмбеддера проверяется вместе с префиксом и специальными токенами; слишком длинный текст не обрезается молча.

Новая коллекция строится при изменении корпуса, стратегии или параметров чанкинга, представления текста для эмбеддера, формата или размерности вектора, ревизии модели, настроек построения HNSW или обработки текста для гибридного поиска. Параметры поискового запроса, эталоны и размер пакета документов идентификатор индекса не меняют. В плотном режиме настройки BM25 не участвуют в его расчёте. Готовая совместимая коллекция используется целиком; `--rebuild` выполняет полную сборку. Промежуточные чанки и векторы не кэшируются; при переходе с плотного поиска на гибридный создаётся новая коллекция.

Завершены запуски всех 10 конфигураций, включая [базовый профиль G1](g1_splitters/markdown.yaml). В снимке настроек зафиксированы один шард, тип вектора float32, косинусное сходство, `indexing_threshold=1` КБ для сборки и `full_scan_threshold=10` КБ для планировщика поиска. Если после перезапуска готовая коллекция переходит в состояние `grey`, для возобновления оптимизации меняется только число рабочих потоков (`max_optimization_threads` — 1 или 2). Действие сохраняется в метаданных коллекции. См. [карту групп и базовых конфигураций](study.yaml) и [результаты сравнения](../../docs/rag/EXPERIMENTS.md).

## Устройство Study и зависимости

### Зависимая группа и зависимая конфигурация

**Зависимая группа** использует результаты предыдущего этапа для выбора исходного профиля. Например, перед G2 нужно закончить G1 и выбрать стратегию чанкинга; перед G3 и G5 — выбрать плотную базу после G2. Это отмечается `requires_base: true`. У G1 значение `false`: для первого baseline не нужны результаты предыдущей группы.

**Зависимая конфигурация** — вариант, полный набор параметров которого уточняется после такого выбора. Если в G1 выиграл `source_map_recursive`, оба YAML G2 должны содержать именно эту стратегию и остальные параметры победителя. Затем в одном меняется только перекрытие, в другом — только размер чанка. Зависимость относится к постановке эксперимента: каждый YAML всё равно содержит все настройки и может запускаться самостоятельно.

Карта не подставляет значения из базового файла. Автор копирует выбранный профиль в новые пресеты, меняет нужные поля и записывает связь с завершённым запуском. При запуске с `--study` и `--group` программа проверяет, что эта связь и фактические отличия соблюдены. Без этих флагов `experiment` выполняет самостоятельный запуск без проверки карты.

### `selected_base_run` и `reference_run`

- **`selected_base_run`** — имя уже завершённого запуска, выбранного базой и общим контролем группы. Например, `g1_source_map_recursive` означает каталог `results/g1_source_map_recursive/`; параметры контроля берутся из его сохранённого `config.yaml`.
- **`reference_run`** — контроль для конкретного сравнения в `comparisons`. Если поле не задано или равно `null`, используется `selected_base_run`. У зависимой группы явно заданный контроль должен совпадать с её выбранной базой.
- **`run`** внутри сравнения — имя запуска самого проверяемого варианта. Оно связывает запись карты с его сохранёнными результатами. Новое имя исполнения задаёт `--experiment-name`, а ссылку в карте автор обновляет после завершения.

Например, у G2 база — `g1_source_map_recursive`, а у варианта с увеличенным перекрытием `run=g2_overlap_128` и `reference_run=g1_source_map_recursive`. Так видно, относительно чего измерено изменение качества.

**База группы и победитель её экспериментов — разные роли.** В текущей G1 `selected_base_run=g1_markdown_initial`: Markdown остаётся контролем для двух других стратегий. Победитель G1 — `g1_source_map_recursive` — становится `selected_base_run` уже в G2. Для первоначального baseline G1 в карте записан `reference_run: null`; сводка убирает ссылку запуска на самого себя.

### Откуда берётся `selection_reason`

`selection_reason` — текстовое обоснование выбора базы, которое **вручную формулирует автор экспериментов: человек или агент**. Команда не генерирует его автоматически. В текущей карте обоснования опираются на сохранённые результаты выполненной серии.

Порядок выбора задан программой экспериментов: сначала Evidence Coverage@5, затем MRR@10, после этого затраты и объём возвращаемого текста. Автор смотрит агрегаты в `metrics.json`, изменения отдельных вопросов в `per_question.jsonl`, времена и размер индекса, затем объясняет решение в карте. Например: «У source_map EC@5 = 0.9700 против 0.841667 у Markdown; покрытие улучшилось на четырёх вопросах без ухудшений, поэтому этот профиль выбран базой G2».

Текст может объяснять и ограничение постановки. В G4 гибридная база выбрана потому, что группа исследует настройки гибридного поиска; превосходство над плотным поиском для этого не требуется. В G1 обоснование также описывает итог сравнения и выбор стратегии для следующей группы, хотя контроль самой G1 остаётся Markdown.

Для зависимой группы обоснование должно быть заполнено. Программа проверяет наличие текста и совместимость запусков, но содержательную убедительность объяснения оценивает автор или рецензент. Поле `qa_selection.reason` имеет похожее назначение: объясняет окончательный выбор retrieval-профиля для QA20 по всей серии.

### Пример записи

Сокращённая карта с одной группой и одним уже выполненным вариантом G2:

```yaml
schema_version: 1
groups:
  G2:
    requires_base: true
    selected_base_run: g1_source_map_recursive
    selection_reason: >-
      В G1 выбран source_map_recursive H4: EC@5 = 0.9700,
      MRR@10 = 0.9750. Он становится контролем для изменения размера и перекрытия.
    comparisons:
      - config: configs/experiments/g2_chunks/overlap_128.yaml
        run: g2_overlap_128
        reference_run: g1_source_map_recursive
        changed_parameters:
          - chunking.chunk_overlap
```

Запись означает: сравнить сохранённый вариант 512/128 с контролем 512/64; полный пресет варианта лежит в указанном `config`. `changed_parameters` перечисляет отличия эффективных настроек от снимка контроля. Если заодно изменить стратегию или title, не отразив это в списке, проверка перед запуском завершится ошибкой.

### Поля карты

Здесь `group` обозначает объект внутри `groups.G1`, `groups.G2` и т. д., а `comparison` — один элемент его списка `comparisons`.

| Поле | Тип / default | Значение |
| --- | --- | --- |
| schema_version | int, обязательно | Только 1. |
| groups | mapping[str, group], обязательно | Имена групп и их описания, например G1–G5. |
| qa_selection | object/null, null | Окончательно выбранный retrieval-профиль для QA20. |
| qa_selection.run | str, обязательно в object | Имя завершённого retrieval-run. |
| qa_selection.config | str, обязательно в object | Путь к полному YAML выбранного профиля относительно проекта. |
| qa_selection.reason | str, непустая | Обоснование итогового выбора по сохранённым сравнениям. |
| group.requires_base | bool, обязательно | Нужен ли предварительный выбор базы: G1 false, G2–G5 true. |
| group.selected_base_run | str/null, null | Общая база группы; null блокирует запуск зависимой группы. |
| group.selection_reason | str/null, null | Авторское объяснение выбора базы; обязательно для запуска зависимой группы. |
| group.comparisons | list[object], обязательно | Пресеты, запускаемые и сравниваемые в группе. |
| comparison.config | str, обязательно | Путь от корня проекта; однозначно сопоставляется с `--config`. |
| comparison.run | str/null, null | Имя сохранённого результата варианта; до его выполнения может быть null. |
| comparison.reference_run | str/null, null | Контроль сравнения; при null используется база группы. |
| comparison.changed_parameters | list[str], [] | Точные пути изменённых полей, например `chunking.chunk_overlap`. |

### Как заполняется карта и что проверяет запуск

1. Пока база зависимой группы не выбрана, `selected_base_run` остаётся `null`, а её полные YAML считаются предварительными заготовками.
2. После анализа предыдущей группы автор выбирает завершённый retrieval-run, записывает его имя и обоснование, уточняет полные пресеты и списки `changed_parameters`.
3. Перед запуском с картой проверяются выбранная база, завершённость контрольного retrieval-run, совпадение корпуса и эталонов, точное соответствие объявленных и фактических изменений. У зависимой группы явно указанный `reference_run` обязан совпадать с `selected_base_run`.
4. После завершения автор указывает имя результата в `comparison.run`. Runner сам не редактирует `study.yaml` и не запускает следующую группу.

Название группы, фактический контроль, изменённые параметры и обоснование копируются в `run.json` во время выполнения. Последующая правка карты не меняет этот снимок: карта отражает текущую организацию сравнений, паспорт — условия конкретного запуска.

## Программа G1–G5

Все группы используют один корпус, одни 20 эталонных вопросов и одну закреплённую ревизию EmbeddingGemma 2. Базовый профиль: плотный поиск, чанки 512/64, размерность 768, `include_title=true`, `strip_markdown_headings=false`, HNSW 16/100/128, без квантования. Конкретные полные параметры находятся в YAML; ниже указаны изменения относительно контроля каждой группы.

Стрелки показывают, результаты каких групп используются при выборе базы следующего сравнения:

```mermaid
flowchart LR
    G1["G1: стратегия чанкинга"] --> G2["G2: размер и перекрытие"]
    G2 --> G3["G3: плотный и гибридный поиск"]
    G3 --> G4["G4: настройки гибридного индекса и поиска"]
    G2 --> G5["G5: заголовки во входе эмбеддера"]
```

| Группа | Текущая база / контроль | Пресетов в группе |
| --- | --- | --- |
| G1 | `g1_markdown_initial` | 3, включая исходный baseline. |
| G2 | `g1_source_map_recursive` — победитель G1. | 2 новых варианта. |
| G3 | `g1_source_map_recursive` — выбранная плотная база после G2. | 1 новый вариант. |
| G4 | `g3_hybrid` — гибридная база G3. | 2 новых варианта. |
| G5 | `g1_source_map_recursive` — та же плотная база после G2. | 2 новых варианта. |

Итого 10 уникальных конфигураций: 3 + 2 + 1 + 2 + 2. Контроли из предыдущих групп используются по ссылке на готовый run; отдельный повторный эксперимент для каждой такой ссылки не нужен. Это последовательная программа сравнений; все возможные сочетания параметров не перебираются.

### G1 — стратегия чанкинга

**Вопрос:** влияет ли способ разбиения правил на возможность найти нужные доказательства? Меняется только `chunking.strategy`; размер 512, перекрытие 64, настройки поиска и подготовки embedding input остаются базовыми.

| Пресет | Что делает | Что проверяем |
| --- | --- | --- |
| [g1_splitters/markdown.yaml](g1_splitters/markdown.yaml) | MarkdownTextSplitter по целой книге, с Markdown-разделителями как ориентирами. Run: `g1_markdown_initial`. | Исходная точка сравнения: насколько достаточно разбиения с учётом Markdown-структуры. |
| [g1_splitters/recursive.yaml](g1_splitters/recursive.yaml) | RecursiveCharacterTextSplitter по целой книге со стандартными разделителями. Run: `g1_recursive`. | Как меняется поиск при разбиении без специальной привязки к Markdown-заголовкам. |
| [g1_splitters/source_map_recursive.yaml](g1_splitters/source_map_recursive.yaml) | Границы по source_map до H4, затем Recursive внутри каждого участка. Run: `g1_source_map_recursive`. | Помогают ли границы разделов получать более тематически цельные фрагменты и лучше покрывать эталонные факты. |

Первые две стратегии могут пересекать границы разделов; в третьей исходные участки разделены по карте. Вводный текст родителей сохраняется, overlap действует внутри участка. На выполненном наборе выбран `source_map_recursive`; его профиль 512/64 стал контролем G2.

### G2 — размер чанка и перекрытие

**Вопрос:** улучшится ли полнота найденных доказательств, если увеличить повторяющийся текст на стыках или вместить больше текста в один чанк? База — выбранная стратегия G1 с 512/64. Два изменения проверяются независимо.

| Пресет / run | Изменение относительно 512/64 | Зачем менять |
| --- | --- | --- |
| [g2_chunks/overlap_128.yaml](g2_chunks/overlap_128.yaml), `g2_overlap_128` | `chunk_overlap`: 64 → 128; `chunk_size=512`. | Больше общего текста соседних чанков может помочь найти правило, разрезанное границей. Цена — больше дублирования и объём индекса/контекста. |
| [g2_chunks/size_768.yaml](g2_chunks/size_768.yaml), `g2_size_768` | `chunk_size`: 512 → 768; `chunk_overlap=64`. | Больший фрагмент может вместить правило вместе с условиями и исключениями. Цена — больше текста на один результат и возможное снижение точности локализации. |

Это сравнение качества и затрат. При смене разбиения заново определяется множество релевантных чанков: знаменатель chunk-level Recall меняется. Поэтому основной критерий выбора — Evidence Coverage@5 по общим эталонным диапазонам; учитывается и объём возвращаемого текста. После G2 сохранена исходная плотная база 512/64; она используется в G3 и G5.

### G3 — плотный и гибридный поиск

**Вопрос:** добавит ли поиск по словам полезные результаты к поиску по смысловой близости? Контроль — лучшая плотная база после G2. Новый пресет [g3_search/hybrid.yaml](g3_search/hybrid.yaml), run `g3_hybrid`, меняет только `retrieval.mode`: `dense` → `hybrid`.

Плотная ветвь ищет близкие векторы текста. Гибридный режим добавляет нативный BM25 по исходному `page_content`; Qdrant объединяет ранги через RRF. Проверяется, помогает ли лексическая ветвь с точными названиями, терминами и формулировками, которые плотный поиск мог поставить ниже.

Параметры гибридной базы: по 20 кандидатов каждой ветви, RRF с константой 2 и равными весами; BM25 `k1=1.2`, `b=0.75`, lowercase, Snowball English и English stopwords. Остальные параметры берутся из плотной базы. Итоговая выдача для оценки — до 10 результатов. Гибридный пресет строит собственную полную коллекцию с обоими индексами.

### G4 — настройки HNSW и BM25 в гибридном поиске

**Вопрос:** как влияют настройки приближённого векторного поиска и лексической ветви на гибридную выдачу? Оба новых пресета независимо сравниваются с **одной базой `g3_hybrid`**, даже если в G3 плотный поиск оказался лучше.

| Пресет / run | Что варьируется | Зачем менять |
| --- | --- | --- |
| [g4_index/hnsw_32_200_256.yaml](g4_index/hnsw_32_200_256.yaml), `g4_hnsw_32_200_256` | `index.hnsw.m`: 16 → 32; `ef_construction`: 100 → 200; `retrieval.ef_search`: 128 → 256. BM25 остаётся базовым. | Более связный граф и более широкий поиск при построении и запросе могут повысить точность приближённого поиска. Проверяется, оправдывает ли изменение качества дополнительные затраты памяти и времени. |
| [g4_index/bm25_no_stem.yaml](g4_index/bm25_no_stem.yaml), `g4_bm25_no_stem` | `bm25.stemmer`: Snowball English → null; `k1`: 1.2 → 1.5; `b`: 0.75 → 0.5. HNSW остаётся 16/100/128. | Проверяется профиль без сведения слов к общей основе. Больший `k1` ослабляет насыщение влияния повторов терма, меньший `b` — поправку на длину документа. Меняется баланс точного лексического совпадения и ранжирования длинных чанков. |

Второй вариант берётся прямо от G3, поэтому не включает усиленный HNSW первого. Lowercase, English stopwords, число кандидатов, веса и RRF остаются базовыми. В каждом пресете меняются несколько параметров: вывод относится к профилю целиком; отдельный эффект каждого параметра эта группа не изолирует.

### G5 — заголовки в представлении для эмбеддера

**Вопрос:** помогает ли дополнительный путь раздела в embedding input и что даёт удаление исходных Markdown-заголовков из этого же входа? Контроль — плотная база после G2, `include_title=true` / `strip_markdown_headings=false`.

| Пресет / run | Пара title / strip | Что проверяем |
| --- | --- | --- |
| Контроль `g1_source_map_recursive` | `true / false` | В отдельном title есть книга и пути разделов, исходные заголовки сохраняются в тексте. |
| [g5_headings/title_strip.yaml](g5_headings/title_strip.yaml), `g5_title_strip` | `true / true`; меняется только `embedding.strip_markdown_headings`. | Поможет ли убрать повторение заголовков в основном тексте, сохранив тематическую подсказку в title. |
| [g5_headings/no_title_keep.yaml](g5_headings/no_title_keep.yaml), `g5_no_title_keep` | `false / false`; меняется только `embedding.include_title`. | Как влияет отключение дополнительного title при сохранении исходного текста с заголовками. Формат входа использует `title: none`. |

Меняется только производный вход эмбеддера. Исходный `page_content`, геометрия чанков и координаты цитирования одинаковы у трёх вариантов. Используется плотный поиск, чтобы лексическая ветвь BM25 не влияла на сравнение embedding input. Четвёртая комбинация `false / true` поддерживается кодом, но не входит в обязательные 10 конфигураций.

## Сводка результатов CSV

### Как получить и читать сводку

```bash
uv run python -m dnd_rag summarize-results \
  --study configs/experiments/study.yaml \
  --output results/retrieval_comparison.csv
```

Команда читает карту и сохранённые `run.json` / `metrics.json`; модели, Qdrant и новый retrieval для этого не нужны. Сводку можно пересоздать; файлы завершённых запусков при этом не меняются. Пути к паспортам и снимкам конфигураций включены в CSV.

Строки имеют роль `comparison` (запуск одного из пресетов группы) или `reference` (внешний для этой группы контрольный run). Один контроль может использоваться в нескольких группах без повторной индексации. В текущей [retrieval_comparison.csv](../../results/retrieval_comparison.csv) **14 строк: 10 comparison и 4 reference**. Это результаты 10 уникальных конфигураций. Дополнительный `g1_markdown_reuse_check` проверяет повторное использование коллекции и не входит в обязательное сравнение.

`comparison_cohort` объединяет условия корпуса, эталонов и версии метрик. Для каждой строки проверяются базовый запуск группы и её фактический контроль. Если контроль отсутствует, завершился с ошибкой или несовместим, `comparison_eligible=false`, а `comparison_error` объясняет причину. Для зависимой группы контроль должен совпадать с выбранной базой. Эти проверки работают и после ручного редактирования карты перед offline-summary.

Статусы `failed`, `missing` и `not_run` видны явно; неуспешному запуску не приписываются метрики успешного. Метрики разных запусков не усредняются. Для сравнения используйте совместимые строки; контрольные ссылки помогают сопоставлению, их не следует считать новыми независимыми экспериментами.

### Метрики и объём выдачи

Сводка содержит Precision, Recall и Evidence Coverage при k = 1, 5, 10; MRR@10; число чанков; размер исходных векторов в байтах; средний объём текста (`raw_tokens`) и число результатов (`returned_count`) при каждом k. Числа raw_tokens относятся к токенайзеру эмбеддера и характеризуют расход текста, а бюджет LLM считается отдельно.

### Времена и повторное использование

| Поле / группа полей | Как понимать |
| --- | --- |
| Времена запроса `all` | Минимум, среднее, медиана и максимум по всем 20 вопросам. |
| Времена `warm` | Те же показатели по вопросам 2–20 одного процесса. Первый запрос сохранён отдельно; специального повторения каждого вопроса для прогрева нет. |
| `preparation_ms` | Сумма измеренных стадий: токенайзер, чанкинг, загрузка модели документов, векторизация, загрузка в Qdrant, готовность индекса и BM25 при необходимости. Заполняется для built/rebuilt; при reuse поле пусто. |
| `original_preparation_ms` | Стоимость первоначальной сборки из её сохранённого паспорта, даже если текущий запуск переиспользовал готовую коллекцию. |
| `wall_time_ms` | Весь текущий run: проверки или reuse, подготовка при необходимости, загрузка CPU-модели запросов и обработка 20 вопросов. |

Пропущенные стадии остаются пустыми. Поисковый запуск `experiment` не включает отвечающую LLM. Измерения времени — одиночные запуски с обычными файловыми/HF-кэшами; небольшие различия не доказывают устойчивого преимущества параметров.

## Текущие результаты и выбор для QA

Все 10 конфигураций выполнены. Результат более раннего `g1_markdown_initial` включён по ссылке, остальные 9 вариантов построены с нуля без кэшей промежуточных стадий. Выбран плотный поиск `source_map_recursive` до H4, размер чанка 512 токенов, перекрытие 64, `include_title=true`, `strip_markdown_headings=false`: EC@5 = 0.9700, MRR@10 = 0.9750 на 20 эталонных вопросах.

Окончательный выбор записан в `qa_selection`: `run` указывает на сохранённый retrieval-run, `config` — на полный YAML, `reason` — на обоснование по всей серии. Выбор опирается на те же 20 вопросов и не доказывает общей оптимальности профиля. Смысловое качество ответов LLM оценивается отдельно.
