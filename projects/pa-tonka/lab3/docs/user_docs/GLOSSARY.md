## Session

Диалог из нескольких пользовательских реплик и ответов агента. Программный `session_id` связывает его историю, вызовы MCP и записи Langfuse. Новый диалог получает новый идентификатор. Native ID сессии Codex хранится отдельно: адаптер использует его для `exec resume`.

## Turn

Обработка одного пользовательского запроса до возвращённого ответа, включая промежуточные обращения к LLM и инструментам. `turn_id` идентифицирует эту операцию. У собственного агента лимиты 12 LLM / 16 tools / 300 секунд относятся к агентному циклу одного `AgentService.ainvoke` и сбрасываются при следующем запросе.

## Thread_id

Ключ состояния диалога в LangGraph, передаваемый как `configurable.thread_id`. В собственном агенте он равен `session_id`. Это логический идентификатор истории, а не поток ОС.

## InMemorySaver

Встроенное хранилище контрольных состояний LangGraph: сохраняет сообщения и результаты инструментов по `thread_id` в памяти Python-процесса. Создаётся в [AgentService](../../src/dnd_rag/agent/service.py). Оно переживает следующие реплики того же запущенного сервиса, но не перезапуск процесса. Отдельный JSONL-журнал на диске служит для аудита; автоматическое восстановление checkpointer из него не реализовано.

## AgentReply

Объект результата `ainvoke`, определённый в [agent/contracts.py](../../src/dnd_rag/agent/contracts.py). Поле `text` содержит ответ, `status` — исход обработки, `error` — код/описание ошибки при наличии, `usage` — измерения, `sources` — источники, `trace_id` — идентификатор trace. Ошибка внутри обычного агентного цикла также оформляется этим объектом.

## Usage

Измеренные затраты вызова модели или обработки реплики: прежде всего input/output/total tokens. `AgentReply.usage` дополнительно содержит счётчики, время и локальную API-стоимость. Токеновые итоги включают summary; если часть генераций не завершилась и полного расхода нет, соответствующие поля равны `None` (`null` в JSON). Неизвестное значение не означает нулевой расход.

## NativeLLM

Класс [runtime.llm.NativeLLM](../../src/dnd_rag/runtime/llm.py): программная обёртка над локальным llama.cpp API. Создаёт ChatOpenAI-клиент, считает полный вход родным токенайзером GGUF, проверяет бюджет и сверяет count с серверным usage.

## Summary

Текстовая сводка старой части диалога, сгенерированная LLM по [summary.txt](../../src/dnd_rag/agent/prompts/summary.txt). Заменяет эту часть только в активном контексте модели. Исходный журнал сохраняется целиком; точность сохранённых смысловых фактов требует отдельной оценки.

## Compaction

Операция сокращения активной истории. У собственного агента это замена старых завершённых взаимодействий на summary; у Codex — штатный алгоритм готового агента. Логи содержат событие операции. Лимит контекста и физическое окно модели остаются разными ограничениями.

## Context_budget

Код ошибки, когда полный следующий запрос не помещается в порог агента после допустимого сокращения истории либо сокращать ещё нечего. Собственный агент возвращает `AgentReply.status="context_budget"` и `error["code"]="context_budget"`. Текущий пользовательский запрос и его tool results не обрезаются для обхода ошибки.

## Context_overflow

Код ошибки физического окна: `input + output reserve + safety` превышает окно сервера. Проверяется `NativeLLM.ensure_safe`; у собственного агента попадает в `AgentReply.status` и `error["code"]`. Возможен и для входа самого суммаризатора.

## Hit

Один найденный фрагмент книги в массиве `hits` результата `search_rules`. Содержит текст, rank/score, координаты и идентификаторы происхождения. Источники `[n]` назначаются этим фактически полученным фрагментам текущего диалога.

## Conflict

`build_encounter` обнаружил конкретное противоречие обязательных требований: например, обязательное существо не проходит фильтр типа/среды, количества превышают total_count или обязательный состав уже дороже бюджета. Результат содержит `status="conflict"` и пояснение в `error`.

## Search_exhausted

`build_encounter` не нашёл подходящий состав в пределах своего ограниченного перебора. Результат имеет `status="search_exhausted"` и пояснение. Это не доказательство отсутствия решения во всём каталоге и не успешный подбор.

## Proxy

HTTP-посредник. В lab3 [codex_proxy.py](../../src/dnd_rag/runtime/codex_proxy.py) принимает запросы Codex на порту 8081 и обращается к llama.cpp на порту 8080. Преобразует несовместимый формат описания tools; собственный планировщик или compaction в нём отсутствуют.

## Payload

Данные запроса или ответа API. Для LLM это JSON с сообщениями, схемами инструментов, аргументами, результатами и параметрами генерации. Полный вход считается после фактической сериализации payload, а не только по видимому тексту пользователя.

## Wire

Сохранённые фактические HTTP-данные обмена с моделью. Для Codex журнал включает исходный запрос клиента и effective-запрос после преобразования proxy, полученные ответы, native count/usage. Это материал для проверки того, что реально передавалось серверу.

## Rollout

Собственный JSONL-журнал сессии Codex: события, сообщения, tools, ответы, доступный usage и compaction. Находится в используемом `CODEX_HOME/sessions`. «Закрытый rollout» означает, что процесс текущего `exec/resume` закончился и дописывать этот ход больше не будет; последующий resume может продолжить ту же сессию.

## Exporter

Скрипт переноса событий Codex в Langfuse. Используется закреплённый [observability plugin](../../configs/baseline/README.md#экспортер-что-он-переносит): читает rollout, восстанавливает observations и отправляет их в локальный Langfuse. Проект запускает его отдельным Node.js-процессом после каждого хода Codex.

## Readback

Обратное чтение записанных данных через API Langfuse после экспорта. Подтверждает, что ожидаемые observations и последний ответ ассистента действительно доступны в Langfuse. Успешного запуска экспортера самого по себе для этого недостаточно.

## Deduplication

Защита от повторной записи одних и тех же событий при повторном экспорте rollout. Экспортер сохраняет служебное состояние рядом с исходным журналом. Отдельная сквозная проверка сравнивает ID observations до и после повторного экспорта: новые дубликаты появляться не должны.

## Observation

Одна запись Langfuse с типом, временем и данными операции. Общий термин для agent, generation, tool, retriever и обычных spans. Родительские ID образуют дерево выполнения.

## Trace

Группа observations обработки одной реплики. Имеет `trace_id`; связанные traces диалога объединяются через `session_id`. В интерфейсе Langfuse trace показывает дерево LLM, инструментов, retrieval и сокращения истории.

## Generation

Observation вызова генеративной модели: вход, ответ, параметры и доступные токены/стоимость. Это основной узел учёта usage данного вызова. Отдельная копия raw response не должна повторно начислять те же токены в агрегат Langfuse.

## Span

Observation обычной операции, например подготовки контекста или хранения raw response. Может быть родителем вложенных записей. В проектных текстах «span инструмента» также означает observation с типом tool; retrieval имеет свой вложенный узел.

## Runtime

Один управляемый запуск локального стека: подготовка индекса, LLM, MCP/proxy и CLI либо runner. [RuntimeSession](../../src/dnd_rag/runtime/processes.py) управляет принадлежащими этому запуску процессами. Это другая сущность, чем пользовательская session диалога.

## Child process

Дочерний процесс, созданный другим процессом. Например, Python-launcher запускает llama.cpp; CodexRunner — Codex CLI и Node.js-экспортер. В документации «ребёнок» означает такой процесс, а не отдельного агента.

## Process group

Группа процессов Linux с общим PGID. Позволяет остановить запущенную программу вместе с её потомками внутри группы, даже если wrapper завершился первым. Проект создаёт отдельные группы и проверяет владение перед отправкой сигнала.

## Lock

Блокировка, запрещающая два одновременных управляемых запуска одного проекта. [ProjectLock](../../src/dnd_rag/runtime/lock.py) удерживает файловую блокировку `.runtime/project.lock`; второй запуск получает `runtime_busy`. Само наличие файла не означает занятую блокировку.

## FLOCK

Системный механизм файловой блокировки Linux (`fcntl.flock`). Блокировка связана с открытым файловым описанием. Проект не снимает её явным `LOCK_UN`: после закрытия дескриптора родителя живые потомки удерживают блокировку своими унаследованными копиями. Используется для исключения параллельных runtimes и как доказательство владения оставшейся группой процессов.

## Signal

Уведомление процесса от ОС: SIGINT обычно поступает по Ctrl+C, SIGTERM запрашивает завершение, SIGKILL немедленно завершает процесс и не перехватывается. Обработчики проекта используют первые два, чтобы выполнить cleanup. После завершения launcher через SIGKILL живой потомок может сохранить lock.

## Cleanup

Завершение ресурсов запуска: остановка принадлежащих ему процессов/потоков, ожидание выхода и закрытие файловых дескрипторов. Если остановку собственных процессов подтвердить не удалось, runtime сохраняет блокировку. Контейнеры и постоянные данные обычный выход приложения не удаляет.

## Capture

Чтение и сохранение stdout/stderr запущенной программы. Функция [_capture_owned](../../src/dnd_rag/experiments/codex.py) обслуживает Codex и Node.js-экспортер: сохраняет уже прочитанные байты при таймауте или отмене, завершает только подтверждённую собственную группу и ограничивает ожидание закрытия каналов вывода.
