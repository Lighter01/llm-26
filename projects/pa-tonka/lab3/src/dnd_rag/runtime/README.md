# Управление локальным запуском

Модуль готовит сервисы в нужном порядке и завершает ресурсы своего запуска. Один [runtime](../../../docs/user_docs/GLOSSARY.md#runtime) может обслужить несколько диалогов; он не равен пользовательской сессии. Общая схема — в [архитектуре](../../../docs/user_docs/ARCHITECTURE.md#процессы-и-хранилища).

## Порядок запуска

`application_stack` из [application.py](application.py) выполняет последовательность:

1. Получает блокировку проекта и проверяет готовность Qdrant/Langfuse.
2. Проверяет игровой каталог и совместимость индекса; при необходимости строит индекс GPU-worker.
3. Дожидается полного завершения worker, освобождая GPU для GGUF-модели.
4. Запускает llama.cpp, затем MCP и HTTP-посредник Codex.
5. Передаёт готовые сервисы CLI или runner; при выходе выполняет очистку ресурсов.

Готовый индекс используется без загрузки document encoder. Вопросы кодирует CPU `QueryEncoder`. Retrieval-ядро не импортирует и не запускает генеративную LLM.

## Кто владеет ресурсами

| Ресурс | Запуск и завершение |
| --- | --- |
| GPU-worker и llama.cpp | `RuntimeSession` создаёт дочерние процессы в отдельных группах Linux. |
| MCP и Responses proxy | `background_server` запускает Uvicorn в потоках Python; при выходе запрашивает остановку и ожидает завершения. |
| Codex CLI и Node.js-экспортер | [CodexRunner](../experiments/codex.py) отдельно управляет своими дочерними процессами и группами. |
| Qdrant и Langfuse | Docker Compose; выход приложения оставляет контейнеры и постоянные данные. |

[Дочерний процесс](../../../docs/user_docs/GLOSSARY.md#child-process) — отдельная программа, запущенная родительским процессом. [Группа процессов](../../../docs/user_docs/GLOSSARY.md#process-group) объединяет программу и её потомков под PGID, чтобы остановить их вместе. Занятый порт или неопределённая сетевая ошибка не дают права использовать либо завершать чужой сервис.

## Остановка и блокировки

[ProjectLock](lock.py) получает исключительную неблокирующую `fcntl.flock` для `.runtime/project.lock`. Второй управляемый запуск получает `runtime_busy`. Сам файл может оставаться после выхода: занятость определяется системной [FLOCK-блокировкой](../../../docs/user_docs/GLOSSARY.md#flock), а не наличием файла.

Дочерние процессы `RuntimeSession` наследуют открытый lock-дескриптор. При закрытии родитель не снимает блокировку через `LOCK_UN`: живой потомок продолжает её удерживать. Для Codex/exporter используется отдельная наследуемая блокировка владения группой. Это позволяет проверять владение даже после завершения лидера; совпадения пути lock-файла или повторно использованного PGID недостаточно.

| Событие | Поведение |
| --- | --- |
| Обычный выход, ошибка, SIGINT/Ctrl+C или SIGTERM | Выполняется cleanup: остановка собственных потоков/процессов, ожидание выхода и закрытие дескрипторов. |
| Процесс не завершился после SIGTERM | Подтверждённой собственной группе посылается SIGKILL; ожидания после TERM и KILL ограничены пятью секундами каждое. |
| SIGKILL родительскому launcher | Обработчик не вызывается. Живой потомок может сохранить блокировку проекта. |
| Владение группой не подтверждено | Сигнал группе не отправляется. Незакрытые каналы capture Codex отмечаются в stderr. |

На главном потоке `RuntimeSession` временно откладывает обработку SIGINT/SIGTERM во время создания/регистрации процесса и cleanup; затем восстанавливает прежние обработчики. У дочернего процесса TERM не блокируется. Если остановку собственных процессов подтвердить не удалось, runtime сохраняет блокировку.

### Сбор вывода Codex и экспортера

[_capture_owned](../experiments/codex.py) читает stdout/stderr Codex CLI и Node.js-экспортера. Это [capture](../../../docs/user_docs/GLOSSARY.md#capture): уже прочитанные данные сохраняются независимо от отмены задач чтения. При timeout/cancellation завершается только подтверждённая собственная группа. Последнее ожидание закрытия каналов также ограничено; если оставшийся потомок больше не доказывает владение, каналы закрываются с диагностикой, чужая группа не завершается.

## HTTP-посредник Codex

[codex_proxy.py](codex_proxy.py) реализует [proxy](../../../docs/user_docs/GLOSSARY.md#proxy) на `127.0.0.1:8081/v1/responses`. Он принимает запрос Codex 0.167 и обращается к тому же llama.cpp на порту `8080`; запись `8081 → 8080` обозначает эти два HTTP-порта.

llama build 11046 не понимает описания `additional_tools/namespace` установленного Codex. Посредник переносит пять MCP-схем в Responses functions и обратимо преобразует имена в истории и потоковых ответах SSE. Агентный цикл и compaction выполняет Codex. Thinking и лимит ответа задаёт общий профиль LLM.

Фактические исходные и преобразованные JSON-запросы, ответы, native count и серверный usage сохраняются в [wire-журнале](../../../docs/user_docs/GLOSSARY.md#wire) `.runtime/codex-wire/<session>/wire.jsonl`. Он позволяет проверить обмен с моделью независимо от последующего экспорта в Langfuse.

## Карта модуля

| Файл | Ответственность |
| --- | --- |
| [application.py](application.py) | Общий запуск CLI, smoke и экспериментов; фоновые HTTP-сервисы. |
| [index.py](index.py) | `ensure_index`, `prepare_retriever`, `reset_index`; Qdrant, проверка/reuse индекса, GPU-worker. |
| [processes.py](processes.py), [lock.py](lock.py) | `RuntimeSession`, владение группами, сигналы, очистка и блокировка. |
| [preflight.py](preflight.py) | Проверки готовности; различает отказ соединения и неопределённую сетевую ошибку. |
| [llama.py](llama.py), [llm.py](llm.py) | Запуск llama.cpp, клиент `NativeLLM`, полный подсчёт входа и проверка контекста. |
| [codex_proxy.py](codex_proxy.py) | Совместимость Codex с локальным Responses API и запись wire. |
| [__init__.py](__init__.py) | Маркер Python-пакета. |
